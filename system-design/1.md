# 1. System Goal (What you are building)

You are building a:

> **Distributed workload orchestration system with reconciliation-based scheduling**

Let’s name it for clarity:

**Photon Control Plane (PCP)**

It is NOT just a router anymore.

It:

- accepts workload definitions
- schedules them on nodes
- continuously ensures desired state matches actual state
- recovers from failures automatically

---

# 2. Core Design Principles

We keep it grounded in real distributed systems:

### 1. Declarative, not imperative

You don’t say:

> “run this now”

You say:

> “I want 3 replicas of service X”

---

### 2. Reconciliation loop (truth engine)

System continuously fixes drift between:

- desired state
- actual state

---

### 3. Eventually consistent cluster

Nodes may be temporarily inconsistent, but converge.

---

### 4. Stateless control plane (as much as possible)

State lives in a dedicated store.

---

# 4. Component Design

## 4.1 API Server (Control Entry Point)

### Responsibilities:

- Accept workload definitions
- Validate specs
- Store desired state
- Provide query API

### API shape:

```http
POST /pods
GET  /pods
DELETE /pods/{id}
```

### Example object:

```go
type PodSpec struct {
    ID        string
    Image     string
    Replicas  int
    CPU       int
    Memory    int
}
```

---

## 4.2 State Store (Source of Truth)

This is critical.

### Responsibilities:

- Store desired state
- Store node state
- Provide watch/subscribe mechanism (later upgrade)

### Logical model:

```go
type ClusterState struct {
    Pods map[string]PodSpec
    Nodes map[string]NodeInfo
}
```

Later upgrade: replace with Raft-backed store.

---

## 4.3 Scheduler (Placement Engine)

### Responsibility:

Assign pods → nodes

### Inputs:

- PodSpec
- Node list
- Node capacity

### Output:

- Pod → Node assignment

### Version 1 (simple):

```text
Round-robin or hash-based
```

### Version 2 (advanced):

- bin packing
- CPU/memory awareness
- affinity rules

---

## 4.4 Reconciler (MOST IMPORTANT)

This is the “brain loop”.

### Responsibility:

Make reality match desired state.

### Loop logic:

```text
1. Read desired state
2. Read actual state
3. Compare diff
4. Execute actions:
   - create missing pods
   - delete extra pods
   - reschedule failed pods
5. repeat
```

### This is the core idea behind:

Kubernetes

---

## 4.5 Health Monitor

### Responsibility:

Detect node failure

Mechanism:

- heartbeat every N seconds
- mark node unhealthy if missed

Actions:

- remove node from scheduler
- trigger rescheduling

---

## 4.6 Node Agent (Execution Layer)

Runs on every machine.

### Responsibilities:

- receive tasks
- execute workloads
- report status

### API:

```http
POST /run
GET  /status
```

# 5. Data Flow Scenarios

## 5.1 Creating a workload

```text
User → API Server
     → State Store (save desired state)
     → Reconciler detects change
     → Scheduler assigns nodes
     → Node Agents execute
```

---

## 5.2 Node failure

```text
Node stops responding
→ Health Monitor detects failure
→ Scheduler invalidates node
→ Reconciler reschedules workloads
→ New nodes take over
```

---

## 5.3 Scaling a service

```text
User updates replicas = 5
→ State Store updated
→ Reconciler sees mismatch
→ Scheduler assigns new pods
→ Node Agents launch them
```

---

# 6. Key System Invariants

These are rules your system must always enforce:

### 1. Desired state is never modified by nodes

Only API writes it

### 2. Nodes are disposable

Any node can die anytime

### 3. Reconciler is idempotent

Running it twice must not break system

### 4. System converges

Eventually actual state = desired state

---

# 7. Failure Model

We explicitly design for failure:

| Failure          | Handling                         |
| ---------------- | -------------------------------- |
| Node crash       | reschedule pods                  |
| Network delay    | eventual consistency             |
| Split state      | resolved by store (later Raft)   |
| Reconciler crash | restart safely (idempotent loop) |
